# PDF/Word 文档（含图片与表格）解析场景 — 前后端方案完善与 API 接口清单

------

## 一、现有方案缺口分析

| 缺口             | 现状                         | 影响                                       |
| ---------------- | ---------------------------- | ------------------------------------------ |
| 文档格式单一     | 仅支持 Markdown/HTML 解析    | PDF/Word 格式的设计文档、规范文档无法入库  |
| 图片内容丢失     | 无图片提取和处理能力         | 架构图、流程图、截图等关键信息被忽略       |
| 复杂表格缺失     | 仅处理 Markdown 简单表格     | 合并单元格、跨页表格、嵌套表格无法正确解析 |
| 无文件上传管理   | 文档来源仅 Git 仓库          | 无法管理外部上传的 PDF/Word 文件           |
| 无多模态检索     | 检索仅基于文本               | 用户无法通过图片内容或表格数据进行语义检索 |
| 前端无富媒体展示 | 回答区仅展示代码块和文本段落 | 无法渲染图片和结构化表格                   |

------

## 二、后端方案完善

### 2.2 数据管道层扩展 — 多格式解析管道

在现有数据管道层的"文档解析"环节，扩展为统一的多格式解析管道：

```
文件输入 (.md / .html / .pdf / .docx / .txt)
      │
      ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 1: 格式识别与路由                                            │
│                                                                  │
│  .md / .html   → Markdown/HTML 解析器 (现有，不变)                │
│  .pdf          → PDF 解析器 (新增)                                │
│  .docx / .doc  → Word 解析器 (新增)                               │
│  .txt          → 纯文本解析器 (新增)                              │
└──────────────────────────────┬───────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 2: 结构化提取 → 统一输出为 DocElement 列表                   │
│                                                                  │
│  每个 DocElement 包含:                                            │
│  • type: HEADING / PARAGRAPH / TABLE / IMAGE / CODE_BLOCK / LIST │
│  • content: 文本内容 / 表格结构化数据 / 图片引用路径               │
│  • position: 页码、段落序号、页面坐标 (PDF 特有)                   │
│  • heading_path: 所属标题路径 (继承现有设计)                       │
│  • metadata: 图片尺寸 / 表格行列数 / 字体样式等                   │
└──────────────────────────────┬───────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 3: 图片处理管道 (新增)                                       │
│                                                                  │
│  提取图片 → 存储到 MinIO (原图 + 缩略图)                          │
│           → 多模态 LLM API 生成图片描述文本                       │
│           → 关联上下文 (图片前后各 200 字文本)                     │
│           → 图片去重 (perceptual hash)                            │
│           → 过滤无效图片 (尺寸 < 50×50px、纯白/纯黑)              │
└──────────────────────────────┬───────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 4: 表格处理管道 (新增)                                       │
│                                                                  │
│  提取表格 → 结构化为 JSON (含合并单元格 col_span/row_span)         │
│           → 生成表格自然语言描述 (用于向量化嵌入)                  │
│           → 保留 HTML 格式 (用于前端渲染)                         │
│           → 大表格按逻辑行分组切分                                 │
└──────────────────────────────┬───────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 5: 切片引擎 (扩展现有策略)                                   │
│                                                                  │
│  文本切片: 现有策略不变 (H2/H3 章节级)                             │
│  表格切片: 新增规则 (见 2.3)                                      │
│  图片切片: 新增规则 (见 2.3)                                      │
│  混合切片: 图文混排时的上下文保留                                  │
└──────────────────────────────┬───────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 6: 向量化 (扩展)                                            │
│                                                                  │
│  文本 chunk → BGE-M3 文档嵌入 (现有)                              │
│  图片 chunk → 图片描述文本 → BGE-M3 嵌入 (新增)                   │
│  表格 chunk → 表格描述文本 + 表头 → BGE-M3 嵌入 (新增)            │
└──────────────────────────────────────────────────────────────────┘
```

### 2.3 解析工具选型

| 文档格式      | 解析工具                              | 理由                                           |
| ------------- | ------------------------------------- | ---------------------------------------------- |
| PDF（文本型） | **PyMuPDF (fitz)**                    | 速度快、支持表格提取、图片提取、保留布局信息   |
| PDF（扫描型） | **PaddleOCR / Tesseract**             | OCR 识别扫描件中的文字                         |
| PDF（表格）   | **pdfplumber / Camelot**              | 精确提取表格结构（含合并单元格）               |
| Word (.docx)  | **python-docx + mammoth**             | python-docx 提取结构，mammoth 转 HTML 保留样式 |
| Word（表格）  | **python-docx 原生表格 API**          | 支持合并单元格、嵌套表格                       |
| Word（图片）  | **python-docx 内嵌图片提取**          | 提取嵌入图片 + 位置信息                        |
| 图片理解      | **多模态 LLM API (Qwen-VL / GPT-4o)** | 生成图片描述文本，用于语义检索                 |

### 2.4 PDF 解析流程

```
PDF 文件
    │
    ▼
┌──────────────────────────────────────────────────────────────┐
│  1. 判断 PDF 类型                                             │
│     • 文本型 PDF: 可直接提取文字 → 走文本解析路径              │
│     • 扫描型 PDF: 文字极少但有图片 → 走 OCR 路径              │
│     • 混合型 PDF: 部分页面文本、部分页面扫描 → 逐页判断        │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│  2. 逐页提取                                                  │
│     • 文本块: 提取文字 + 字体大小/加粗 (用于推断标题层级)      │
│     • 表格: 使用 pdfplumber 提取，保留合并单元格信息           │
│     • 图片: 提取嵌入图片 + 页面坐标位置                       │
│     • 阅读顺序: 按坐标位置合并为有序元素列表                   │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│  3. 标题层级推断 (PDF 特有)                                    │
│     • Markdown 有明确的 # 标记，PDF 没有                      │
│     • 通过字体大小、加粗、编号格式推断标题层级                  │
│     • 如: 16pt 加粗 → H1, 14pt 加粗 → H2, 12pt 加粗 → H3    │
│     • 构建 heading_path 数组 (与现有设计兼容)                  │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│  4. 跨页元素处理                                              │
│     • 跨页表格: 检测表格是否在页面底部被截断，合并续页          │
│     • 跨页段落: 检测段落是否在页面底部被截断，拼接续页          │
│     • 页眉页脚: 识别并过滤重复的页眉页脚内容                   │
└──────────────────────────────────────────────────────────────┘
```

### 2.5 Word 解析流程

```
Word 文件 (.docx)
    │
    ▼
┌──────────────────────────────────────────────────────────────┐
│  1. 结构提取                                                  │
│     • 段落: 通过样式名识别标题 (Heading 1/2/3) 和正文          │
│     • 表格: 提取所有表格，处理合并单元格 (gridSpan/vMerge)     │
│     • 图片: 提取内嵌图片 (blip 引用) + 位置信息               │
│     • 列表: 提取有序/无序列表结构                              │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│  2. 文档属性提取                                              │
│     • 标题、作者、创建时间 (core_properties)                   │
│     • 目录结构 (如果有 TOC)                                   │
│     • 批注和修订标记 (可选)                                    │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│  3. 统一输出为 DocElement 列表 (与 PDF/Markdown 格式对齐)      │
└──────────────────────────────────────────────────────────────┘
```

### 2.6 切片策略扩展 — 图片与表格

#### 2.6.1 新增切片类型

在现有切片类型（文件级/类级/方法级/块级/H2章节/H3子章节/代码块独立）基础上，新增：

| 切片类型           | 粒度              | 适用场景               | 示例                                |
| ------------------ | ----------------- | ---------------------- | ----------------------------------- |
| **image**          | 单张图片 + 上下文 | 架构图、流程图、截图   | PDF 中的系统架构图                  |
| **table**          | 完整表格          | 配置表、参数表、对比表 | API 参数列表                        |
| **table_fragment** | 大表格的逻辑分组  | 超过 30 行的大表格     | 错误码对照表                        |
| **figure_group**   | 图文组合          | 图片 + 标题 + 说明文字 | "图 3-1 系统架构" + 图片 + 描述段落 |

#### 2.6.2 图片切片规则

| 规则             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| 图片独立为 chunk | 每张图片生成一个独立的 image_chunk，包含：图片文件引用 (MinIO 路径)、图片描述文本 (多模态 LLM 生成)、上下文窗口 (图片前后各 200 字)、图片标题/图注 |
| 图片过滤         | 宽度 < 50px 或高度 < 50px 的图片忽略（图标/装饰）；纯白/纯黑图片忽略；重复图片去重 (perceptual hash) |
| 图文关联         | 图片 chunk 自动关联所在章节的文本 chunk，通过 `DOC_CONTAINS_IMAGE` 关系类型建立关联 |
| 图片描述生成     | 调用多模态 LLM API (Qwen-VL / GPT-4o)，生成 200~500 字的描述文本，作为 chunk 的 content 用于向量化 |

#### 2.6.3 表格切片规则

| 规则                | 说明                                                         |
| ------------------- | ------------------------------------------------------------ |
| 小表格完整保留      | 表格行数 ≤ 30 行：整个表格作为一个 chunk，content = 表格 Markdown/HTML 表示 + 自然语言描述 |
| 大表格逻辑分组      | 表格行数 > 30 行：有分组标题行则按分组切分；无分组则每 20 行切分一个 fragment；每个 fragment 携带表头作为上下文前缀 |
| 表格不跨 chunk 拆分 | 单个表格的行不在两个 chunk 中断开（除非超过 50 行）          |
| 表格自然语言描述    | 为每个表格生成描述文本（用于向量化），如："该表格展示了事务消息的配置参数，共 8 个参数，包括名称、类型、默认值和说明四列" |
| 合并单元格处理      | 解析时记录 col_span / row_span 信息；前端渲染时还原合并效果；向量化时将合并单元格展开为完整文本 |

#### 2.6.4 切片大小控制（扩展）

| 参数                   | 值       | 说明              |
| ---------------------- | -------- | ----------------- |
| 文本 chunk 最大 token  | 1500     | 现有不变          |
| 表格 chunk 最大 token  | 2000     | 表格允许稍大      |
| 图片 chunk 最大 token  | 800      | 图片描述 + 上下文 |
| 表格 fragment 最大行数 | 20       | 大表格切分阈值    |
| 图片最小尺寸           | 50×50 px | 过滤小图          |

#### 2.6.5 切片 ID 命名规范（扩展）

在现有命名规范基础上新增：

| 类型       | 格式                                   | 示例                        |
| ---------- | -------------------------------------- | --------------------------- |
| 图片 chunk | `img_{fileHash8}_{page}_{seq}`         | `img_e5f6g7h8_p3_001`       |
| 表格 chunk | `tbl_{fileHash8}_{page}_{seq}`         | `tbl_e5f6g7h8_p5_002`       |
| 表格片段   | `tbl_{fileHash8}_{page}_{seq}_frag{n}` | `tbl_e5f6g7h8_p5_002_frag1` |

### 2.8 向量化策略扩展

| 数据类型          | 嵌入内容                                           | 嵌入模型 | 说明                         |
| ----------------- | -------------------------------------------------- | -------- | ---------------------------- |
| 文本 chunk (现有) | heading_path + content                             | BGE-M3   | 不变                         |
| 图片 chunk (新增) | image_caption + image_description + context_before | BGE-M3   | 用描述文本代替图片本身做嵌入 |

### 2.9 检索管道扩展

#### 2.9.1 Stage 0 查询理解扩展

新增意图识别类型：

| 新意图   | 示例                     | 处理策略                   |
| -------- | ------------------------ | -------------------------- |
| 图片查询 | "系统架构图是什么样的"   | 优先检索 image 类型 chunk  |
| 表格查询 | "事务消息有哪些配置参数" | 优先检索 table 类型 chunk  |
| 混合查询 | "回查流程（含流程图）"   | 同时检索文本 + 图片 + 表格 |

#### 2.9.2 Stage 1 召回扩展

在现有四路召回基础上，向量语义检索路径增加 `chunk_content_type` 过滤能力：

| 路径            | 扩展                                                     |
| --------------- | -------------------------------------------------------- |
| 路径 A 向量语义 | 增加对 image/table 类型 chunk 的检索（通过描述文本嵌入） |
| 路径 B BM25     | 索引中增加 image_description、table_description 字段     |

#### 2.9.3 精排扩展

精排阶段的 `structural_features` 新增子特征：

| 新特征             | 说明                                                         |
| ------------------ | ------------------------------------------------------------ |
| content_type_match | 候选 chunk 类型是否与查询意图匹配（如用户问"架构图"，image 类型加分） |
| has_visual         | 候选是否包含图片/表格（有视觉信息的回答更丰富）              |

### 2.10 LLM Prompt 组装扩展

最终 Top-K 结果中如果包含图片/表格 chunk，Prompt 组装策略：

| chunk 类型 | Prompt 中的呈现方式                                          |
| ---------- | ------------------------------------------------------------ |
| 文本 chunk | 直接放入原文（现有）                                         |
| 图片 chunk | 放入 image_description + image_caption + context_before/after，并标注 `[图片: {image_caption}]` |
| 表格 chunk | 放入 table_html 或 Markdown 表格 + table_description         |
| 表格片段   | 放入表头 + 片段内容 + "（完整表格共 N 行，此处为第 M~K 行）" |

### 2.11 增量更新扩展

现有增量更新仅处理 Git 仓库中的 `.java` 和 `.md` 文件变更，扩展为：

| 触发方式           | 说明                                              |
| ------------------ | ------------------------------------------------- |
| Git Webhook (现有) | 代码/Markdown 变更                                |
| 文件上传 (新增)    | 用户上传 PDF/Word → 触发解析管道                  |
| 文件替换 (新增)    | 用户重新上传同名文件 → 增量对比更新               |
| 文件删除 (新增)    | 用户删除已上传文件 → 标记相关 chunk 为 is_deleted |

### 2.12 模型部署扩展

在现有本地 GPU 部署方案基础上，新增 API 调用场景：

| 场景         | 调用频率           | 推荐模型               | 说明                          |
| ------------ | ------------------ | ---------------------- | ----------------------------- |
| 图片描述生成 | 文档解析时批量触发 | Qwen-VL / GPT-4o (API) | 多模态理解，本地 GPU 无法运行 |
| 表格描述生成 | 文档解析时批量触发 | DeepSeek-V3 (API)      | 纯文本任务，成本低            |
| OCR 识别     | 扫描件 PDF 解析时  | PaddleOCR (本地 CPU)   | 不需要 GPU                    |

## 七、一句话总结

在现有 Markdown 解析基础上，新增 **PDF/Word 多格式解析管道**（PyMuPDF + python-docx + OCR），引入 **图片处理管道**（提取 → MinIO 存储 → 多模态 LLM 描述 → 文本嵌入）和 **表格处理管道**（结构化提取 → 合并单元格 → 自然语言描述 → 分片），扩展切片类型（image / table / table_fragment / figure_group），前端新增 **文档管理页**（上传/解析进度/预览）和 **图片/表格引用块**（缩略图放大、HTML 表格渲染），新增 **11 个 API 接口**（文档管理 8 个 + 资源访问 3 个），修改 5 个现有接口以支持多模态检索结果的展示。
