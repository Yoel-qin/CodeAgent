## 0. 阅读说明

这是一份**面向落地编码**的实施计划，不是设计文档本身。设计细节以上述 7 份设计文档为准；本文件负责：

1. **定方案**——把设计文档中相互冲突/含糊的地方收敛为一套可执行的技术决策（详见 [§3 架构决策](#3-关键架构决策解决文档冲突)）。

## 1. 项目定位（一句话）

构建一套面向大型 Java 代码库（设计文档以 RocketMQ 为蓝本）的**代码 + 文档智能知识库**：融合语义向量、GNN 图向量、三阶段检索精排与 GraphRAG 社区摘要，通过多 Agent 体系实现"代码理解 / 文档问答 / 变更影响 / 缺陷诊断 / 代码审查 / 测试生成 / 文档维护 / 新人引导 / 全局问答"九大场景，并支持增量更新、文档腐化检测与代码回滚恢复。

**核心差异化**（相对普通 RAG）：
- 语义向量（理解文本）+ 图向量（理解结构角色）+ 精排（精准挑选）+ 社区摘要（全局视野），四者互补。
- 代码 ↔ 文档双向锚点关联、调用图递归遍历、变更/回滚感知。

## 3. 关键架构决策（解决文档冲突）

> 设计文档之间存在若干不一致（详见 [待确认问题清单.md](./待确认问题清单.md)）。下表是本计划的**默认裁决**，理由见右列。确认前按此推进。

| # | 冲突点 | 默认裁决 | 理由 |
| --- | --- | --- | --- |
| D1 | 向量库：`技术栈.md`=Chroma vs `后端.md`=Milvus | ✅ **Milvus 全程**（已确认） | 后端设计、API 监控指标、HNSW/IVF 配置均围绕 Milvus 的多向量字段（graph_embedding）展开；Chroma 不支持单 collection 多向量，无法承载图向量检索路径 |
| D2 | 图存储：`技术栈.md`=Neo4j 主力 vs `后端.md`=PG call_graph + DGL GNN（Neo4j 可选） | **PG call_graph + 递归 CTE 做 BFS**，GNN 用 **DGL/PyG**，Neo4j 作为**可选可视化/探索**组件 | 后端设计把"真相"放在 PG（调用边、社区、关联、变更历史都在 PG），Neo4j 仅 `graph_traverse` 工具可选；先不引入 Neo4j 以降低复杂度 |
| D3 | 代码嵌入：Voyage Code vs CodeBERT vs UniXcoder | ✅ **CodeBERT**（`microsoft/codebert-base`，768d，本地 `model_server`）；`EMBEDDING_STRATEGY=dual` 启用，`=unified` 则全 BGE-M3 | 用户指定 CodeBERT（2026-07-27，见 Q8）；CodeBERT 非托管 API → 须本地加载 |
| D4 | 粗排：ColBERTv2 vs bge-reranker-base | **bge-reranker-base**（统一用 bge 家族，部署简单） | ColBERTv2 需独立索引与服务，初期收益不大；`§19` 也按 bge-reranker-base 预算 |
| D5 | 嵌入维度：768/1024/3072 不统一 | ✅ 代码 **768d**(CodeBERT) / 文档 **1024d**(BGE-M3)；图嵌入维度随图向量移除作废 | Milvus 各 collection 分别建（unified 单 collection + kind 过滤 / dual 双 collection） |
| D6 | 全文检索：PG tsvector vs Elasticsearch | **Elasticsearch**（BM25 主路径），PG tsvector 作为文档正文 fallback | `后端.md` 明确 ES 负责 BM25；PG 不背全文检索主负载 |
| D7 | 认证 | 单用户模式，预留 JWT 中间件（`python-jose + passlib`） | `api 接口清单` 注明"单用户可省略" |
| D8 | 目标代码库 | ✅ **通用可配置**，先用中小型 Java 仓库跑通全链路（已确认） | 系统与具体仓库解耦，`repo_path` 配置化 |
| D9 | GPU 部署 | ✅ 嵌入**默认走 API 不用 GPU**（unified，2026-07-25）；**dual 框架代码侧重启本地 `model_server`**（CodeBERT，GPU 优先 CPU 回退，2026-07-27 补充） | 默认 unified 不依赖 GPU；文档侧仍走 API。本机 RTX 4050 6GB |
| D10 | 部署架构 | ✅ **后端/前端/model_server 在本地 host 跑；Docker 只跑基础设施**（PG/Redis/MinIO/ES/Milvus/etcd/attu）。infra 端口映射到 host，本地经 localhost 连（2026-07-25 调整） | 降 Docker 内存；应用本地便于热重载调试 |

## 5. 分阶段开发计划

> 设计文档给出 8 个 Phase（约 5 个月）。这里把它们细化成**可逐天推进、有验收标准**的开发序列，并插入前端、PDF/Word、回滚三条横切线。每个 Phase 的任务粒度见 [开发清单.md](./开发清单.md)。

### Phase 0 —— 基础设施与脚手架（~3–5 天）

**目标**：一条 `docker compose up` 拉起全部基础服务，仓库骨架可编译可跑。

- **第 0 步（优先）：WSL2 GPU 透传验证 spike**——确认本机 GPU 能否被 Docker 容器调用（跑一个 `nvidia-smi`/最小 CUDA 探针容器）。通过 → model_server 走 GPU；未通过 → 锁定 API/CPU 回退方案。**此项决定后续模型部署形态，先做。**
- docker-compose：postgres16 + redis7 + minio + elasticsearch8 + **Milvus 全套（etcd + minio + milvus + attu）** + nginx（不引入 Chroma / Neo4j）
- GPU profile（视 spike 结果）：`model_server` 容器 + NVIDIA Container Toolkit（WSL2）；API/CPU 回退开关
- 后端骨架：FastAPI + 配置 + 日志 + 健康检查 + `/api/v1` 路由占位
- DB：Alembic 初始化，建 §10 全部表（含 §18 回滚字段、PDF/Word 扩展字段、`doc_resources`）
- 前端骨架：Vite + AntD + 路由 + 三栏布局壳 + Zustand + axios/SSE 客户端
- Makefile / `make up dev ingest test`

**验收**：`docker compose up` 全绿；`/health` 返回各组件状态；前端首页可访问；Alembic upgrade 成功。

### Phase 1 —— 基础 RAG 主干（~2–3 周）

> 对应设计 §16.1 Phase 1–5（不含图）。先把"代码/文档 → 检索 → 流式回答"这条最短闭环打通。

1. **代码解析（tree-sitter Java）**：文件/类/方法 AST，提取定位/语义/结构/关系/锚点，输出 §3.1.3 结构。
2. **Markdown 解析**：保留标题路径（heading_path）、识别 `CODE_ANCHOR`。
3. **切片**：方法级默认 + 小文件合并 + 超长二次切分（§4.1）；文档 H2/H3 章节级（§4.2）。
4. **元数据 + content_hash + 锚点 key**：写入 `code_chunks` / `doc_chunks`。
5. **关联构建**：`DOC_TO_CODE`/`CODE_TO_DOC`（锚点精确匹配 + 模糊补充）、`call_graph`（调用表达式）、`CODE_IMPLEMENTS`/`CODE_EXTENDS`、`CO_FILE`/`CO_MODULE`。
6. **向量化**：双模型嵌入（先 BGE-M3 跑通，再接 CodeBERT/UniXcoder）→ Milvus `code_chunks`/`doc_chunks` collection。
7. **全文索引**：ES 索引 content+javadoc+keywords、content+heading_path。
8. **一致性**：PG 先写 → Milvus → ES；`embedding_synced` 补偿。
9. **检索**：Stage 0 查询理解 + 路径 A 向量召回（先单路）。
10. **生成**：Prompt 组装 → LLM 流式 → SSE（token/citation/done 事件）。
11. **API**：`POST /chat/completions`（SSE）、会话列表/详情、检索详情、反馈、追问。
12. **前端 P0**：智能问答页（对话流 + 代码/文档引用块 + 右侧上下文面板）+ 输入区/Agent 选择器。

**验收**：对示例仓库提问能得到带引用的流式回答；引用可跳转到源码行/文档章节。

## 6. 数据流与一致性策略（落地要点）

- **写入顺序**：PG（事务）→ Milvus → ES；失败置 `embedding_synced=FALSE`，补偿任务重试。
- **chunk_id** 全局唯一键贯穿四库；命名规范见设计 §4.3 + PDF/Word §2.6.5。
- **锚点** `ClassName.methodName` 为代码↔文档关联核心；失效走 §6.4 流程（软删除 + stale 标记 + 文档维护触发）。
- **增量**：Git Webhook/轮询 → `git diff` → 按扩展名分流 → content_hash 对比 → ADDED/MODIFIED/DELETED（+ ROLLBACK/RESTORED）→ 多库同步 + 图嵌入局部更新。
- **检索预算**：检索管道 ~250ms（召回 30 / RRF 5 / 粗排 40 / 精排 150），LLM ~2s；SSE 逐 token。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| Windows Docker GPU 透传不稳定 | 优先 CPU 跑通逻辑；模型服务可独立 host 或走 API；预留 device 配置开关 |
| Milvus 全套（etcd+minio+milvus）重 | MVP 阶段用 Chroma 跑通单向量路径，Phase 5 前切 Milvus 以支持 graph_embedding |
| 图向量/GNN 训练依赖 GPU + 数据量 | Phase 5 前可先用 Node2Vec 占位；图向量为"加分项"，主链路不依赖它 |
| 社区摘要质量依赖 LLM 成本 | 离线批量、缓存、增量重算只对受影响社区 |
| 多模态解析（表格/扫描件）复杂 | 分级支持：先文本型 PDF/docx，再表格，再 OCR 扫描件 |
| 范围过大 | 严格按 Phase 推进，每个 Phase 有可独立验收的可运行产物；优先 P0 |
